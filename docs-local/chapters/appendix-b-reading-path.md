# 附录 B　阅读路径指南：按角色读、按目标查、与其他素材对表

> 基于 DeerFlow 最新源码（本仓库 commit 2672e209，2026-09）编写。本仓库快照版本 2.1.0。
> 本文是《DeerFlow 深度说明书》的阅读入口：它不重复任何一章的内容，只回答三个问题——
> ① 我是谁、该按什么顺序读；② 我想搞懂 X，该读哪一章、哪篇深文、哪份源码；
> ③ 这套书与旧两书、middleware 深文、官方 AGENTS.md 是什么关系。

## 0. 材料全景：四层素材与它们的"保质期"

动笔读之前，先分清你手上这几份材料的性质——它们不是同一代的东西：

| 素材 | 位置 | 性质 | 代码基准 |
|---|---|---|---|
| **本书（18 章主书）** | `docs-local/chapters/01..18` | 主线说明书，逐章剖析机制 | commit `2672e209`，2.1.0，2026-09 |
| **middleware 深文（8 篇）** | `docs-local/middleware/middleware-01..08` | 第 06 章的外挂深潜：每篇 400–700 行，逐中间件讲"为什么" | 同上 |

| **旧书乙**《DeerFlow 源码解析——ByteDance 开源 Super Agent Harness》 | 仓库外（`coolclaws-deerflow-book`） | 源码解析导向，第 1–23 章 + 附录 A（阅读路径）/B（配置速查）/C（术语表） | 2.0/早期 2.1，`backend/src` 时代 |

## 1. 四条角色阅读路径

四条路径共用同一原则：**先看地图再上路**。地图 = 第 02 章（仓库全景）与第 06 章（中间件链位
地图）；两条主线 = 第 04 章（引擎）与第 05 章（Lead Agent 装配）。下面每条路径给出推荐顺序、
中途可跳的章节，以及"读完你会得到什么"。

### 1.1 路径一：Agent 新手 / 想先把它用起来的人

目标：跑起来、配明白、知道边界在哪。**不读源码，不碰深文。**

1. **第 01 章**（DeerFlow 是什么、为什么）——建立"Harness vs Framework"的心智与全栈拓扑。
2. **第 03 章**（快速上手）——跟着 `make setup` / `make dev` 跑通，验证浏览器与健康检查。
3. **第 02 章 §2.2/§2.8**（目录地图、服务与端口）——只读这两节，其余留给以后。
4. **第 04 章 §4.5**（run 生命周期：准入 → 执行 → 收尾）——知道"一次对话在系统里怎么走"。
5. **第 06 章 §4**（35 链位速查表）——不读机制，只把表当"系统有哪些关卡"的清单扫一遍。
6. 按需回查：**第 12 章**（沙箱模式怎么选）、**第 15 章 §7**（照抄写第一个技能）、
   **第 18 章**（配置往哪改）。

深文一篇都不用读；若想提前建立钩子直觉，只读 `middleware-01` 的 §0（全系列最透的一节心智模型）。
**里程碑**：能独立配置模型/沙箱/工具，会写一个自定义技能，知道出了问题该去哪一章查。

### 1.2 路径二：二次开发工程师 / 要动手改和扩的人

目标：改行为、加能力（工具/MCP/技能/中间件/沙箱 Provider/模型 Provider/扩展）。这是本书
服务的主人群，路径略长但每步都落在一个"可改层"上。

1. **第 02 章**全章——尤其 §2.3 的 **harness/app 依赖红线**（CI 用 `test_harness_boundary.py`
   钉死）与 §2.13 旧书目录对照。改之前不知道这条红线会写出合不进的代码。
2. **第 05 章**（Lead Agent 装配与主循环）——`make_lead_agent`/`assemble_lead_agent`、
   中间件栈装配顺序、系统提示词静态化。这是你多数改动的落点。
3. **第 06 章**全章——链位地图 + §7"自定义中间件写法"。**写中间件前必读**；插入点
   30/31 与"不可改写"的 32–35 是本章最容易踩的坑。
4. **第 18 章**（配置体系与扩展机制）——双层配置、热重载边界（`reload_boundary.py`）、
   **五类扩展贡献点**与 extension-api 契约包。做"扩展"而不是"改源码"时主读这章。
5. 按目标深挖（顺序按你的活来，不是固定序）：
   - 写工具 / 接 MCP → **第 13 章 + 第 14 章**（注册合成、wrap_tool_call 洋葱、延迟路由）；
   - 写技能 → **第 15 章**（激活、授权边界、SkillScan）；
   - 换沙箱 → **第 12 章**（Provider 模式、`SandboxMiddleware` 生命周期）；
   - 接新模型/修 provider 怪癖 → **第 16 章**（能力矩阵、provider 补丁层）；
   - 改 Gateway 路由/认证/IM 渠道 → **第 17 章**；
   - 动上下文注入/压缩/记忆 → **第 07 章 + 第 10/11 章**（见 1.3 的说明）。

深文按职责带查（对照表见 B.2），不必全读；改哪个中间件就读对应那篇的
「源码阅读指引」小节——每篇都给了精确到行的路标。
**里程碑**：能挂一个自定义中间件在链位 30/31，能写一个打包扩展贡献五类能力之一，
能解释自己改的每一处与 harness/app 红线的相容性。

### 1.3 路径三：框架研究者 / 想彻底搞懂机制的人

目标：理解"为什么这么设计"，能给别人讲清楚 35 链位、记忆流水线、子代理账本。**深度优先，
路径最长。**

1. **第 04 章**（LangGraph 引擎与运行模型）——ThreadState/reducer、图抽象、checkpointer、
   RunManager/run_agent、双路径。这是全部机制的底盘。
2. **第 05 章**（Lead Agent）——装配主流程、中间件栈的"共享底座 + lead-only 追加"两段式。
3. **第 06 章**全章——然后**按链位顺序通读 8 篇深文**（第 06 章 §3 给了权威顺序）：
   `01 → 02 → 03 → 04`（共享基座 1–13）→ `05 → 06 → 07`（lead-only 上下文带 14–26）
   → `08`（收尾 27–35）。注意深文个别处用**物理编号**（如 doc-03 把 ToolErrorHandling
   称"第 15 位"），对不上时以第 06 章 §4 的语义链位号为准。
4. **第 07 章**（上下文工程与主线保持）——前缀缓存、三层内存治理、压缩保护、信任分层。
   与 `middleware-05`/`06` 对读，效果最好。
5. **第 10 + 11 章**（记忆架构 + 更新流水线）——从"一次 LLM 抽取、四种组件"到
   "捕获 → 过滤 → 队列 → 提取 → 闸门 → 注入回环"的五站旅程。
6. **第 08 + 09 章**（子代理引擎 + 并发/编排/容量）——持久隔离事件循环、双重预算、
   durable ledger、anti-self-report 三层防线。
7. **第 12 → 13 → 14 → 15 章**（执行与能力面：沙箱/工具/MCP/技能），按主题顺序读。
8. **第 16 → 17 → 18 章**收尾（模型适配 / Gateway 与 IM / 配置与扩展），补齐"平台面"。

想研究"设计是如何演进到今天的"，把旧两书对应章节当对照阅读（见 B.4.3）。
**里程碑**：能不看源码画出 run 生命周期时序图与 35 链位职责表，能讲清一次记忆从对话到
落盘到再注入的完整链路，能说清每个 `stop_reason` 由谁盖章。

### 1.4 路径四：上游贡献者 / 想提 PR 的人

目标：让改动符合仓库的 AGENTS.md 契约与测试门禁。本书不是贡献指南，是"改之前必须懂的
背景"，贡献流程本体在官方文档：

1. 先读仓库根 **`AGENTS.md`**（monorepo 定位层）→ **`backend/AGENTS.md`**（后端深度）
   或 `frontend/AGENTS.md`——它们指向各模块自带的 AGENTS.md（backend 内共 20 份，
   如 `deerflow/AGENTS.md`、`agents/middlewares/AGENTS.md`）。
2. 读 `CONTRIBUTING.md` 与 `docs-local` 之外的 `CHANGELOG_zh.md`，确认主干的提交习惯。
3. 用**第 02 章 §2.11**（scripts、测试与质量门禁）了解 CI 会拦什么——
   `backend/tests/test_harness_boundary.py` 这类契约测试是"架构红线即测试"的代表。
4. 改哪个子系统，先读该书对应章 + 该子系统的 AGENTS.md + `backend/tests/` 里的同名测试
   （用测试反推行为契约，是全书通行的代码导航惯例，见第 01 章）。
5. **注意**：`docs-local/` 是本 fork 自有目录、不随上游同步（见其 README），
   给上游的改动不要落在 `docs-local/` 里。

## 4. 本书与其他素材的关系

### 4.1 与旧两书：同一主题，三代写法

旧两书与本书章节目录高度同构，但**写在不同代码代**上：

- **旧书甲**《DeerFlow 二次开发——理论、架构与源码剖析》（`deerflow-book`，2026-02 前后）：
  实战/二开导向，第 1–14 章 + 附录 A–D。写作于 2.0 发布初期。
- **旧书乙**《DeerFlow 源码解析》（`coolclaws-deerflow-book`）：源码解析导向，第 1–23 章 +
  附录 A（阅读路径）/B（配置速查）/C（术语表）。覆盖到早期 2.1。
- 两书共用**过期的 `backend/src` 时代目录**；本书按 2.1.0（commit 2672e209）的真实布局
  `backend/packages/harness/deerflow/` 全部重写。

书中凡写"旧书/旧资料"，指的就是这两本的合集（章号对应关系因两书结构不同而错位，例如
上下文工程在旧书甲是第 10 章、旧书乙是第 7 章——第 07 章的"旧书对照"正是同时指这两处；
按主题对照即可，不必对章号）。三条最关键的过期信号，旧书只要命中任一条就别照抄：

1. **路径**：`backend/src/...`、`src.models.*`、`src.community.*`、`src.sandbox.*`
   → 现在带 `deerflow.` 前缀，后端包根在 `backend/packages/harness/deerflow`（对照表见
   第 02 章 §2.13，全表是最权威的旧→新映射）。
2. **配置**：`mcp_config.json` → 已被 `extensions_config.json` 取代（加载器按
   extensions_config.json → 遗留 mcp_config.json 查找）；`config.yaml` 顶层
   不再有 `middlewares:` 之类旧结构；默认搜索是 DDG（旧书写 Tavily）。
3. **机制**：中间件不是旧书的"11 层固定链"，现在是 35 链位、由装配代码决定顺序；
   上下文工程主轴从"向量 RAG + 粗暴截断"变成"抽取注入 + 压缩 + durable 投影"。

**旧书还值不值得读？** 值得，但只作两用：① 想理解 2.x 设计演进与历史动机时对照读
（本书讲"现在为什么这样"，旧书帮你看到"它曾经那样"）；② 旧书独有的主题本书暂未展开时

### 4.2 与 middleware 深文：第 06 章的外挂深潜

8 篇深文（每篇 400–700 行）是第 06 章 §4 速查表里"深链"列指向的详细版。分工：

- 第 06 章给**地图与机制**（钩子体系、三段装配、35 链位、插入点）；深文给**单点纵深**
  （每篇结构统一：解决什么问题 → 钩子与链位置 → 伪代码/ASCII 图 → 与邻居协作 →
  设计权衡 → 源码行号指引）。
- 深文按**职责带**分组而非链位连续：01=I/O 通道（1/2/3/+7）、02=基础设施（4/5/6）、
  03=错误处理（8–13）、04=文件安全（11/12 夹心）、05=上下文注入（14–17）、
  06=对话管理（18–22）、07=视觉与路由（23–26）、08=安全守卫与收尾（27–35）。
- 三不读原则：机制没入门别读（先 06 §1 + 01 §0）；只改一个中间件就只读对应那篇的
  「源码阅读指引」小节；把深文当"为什么"，把标注的行号当"读代码的路标"，两者都不替代
  源码本身。

### 4.3 与官方 AGENTS.md 族：布局与契约的基线

官方文档的职责是**定位与契约**（目录在哪、依赖方向、命令、测试布局），本书的职责是
**机制与权衡**（为什么这样、坑在哪、怎么改）。正确的组合读法：

1. **先官方后本书**：改任何子系统，先读根 `AGENTS.md` 找到对应模块指南，再读
   `backend/AGENTS.md`（或 frontend）定位代码，最后回本书对应章要"为什么"。
2. **模块 AGENTS.md 是更深的地图**：backend 内 20 份，例如 `deerflow/AGENTS.md`（harness
   总览）、`agents/middlewares/AGENTS.md`（中间件清单）、`extensions/AGENTS.md`
   （扩展契约）、各子系统的 AGENTS.md。它们随代码更新，是**比任何书都新的目录**；
   书与它冲突时，以它和源码为准。
3. **官方变更文档当裁判**：`CHANGELOG_zh.md`（版本间改了啥）、`config.example.yaml`
   （schema 的 ground truth，配合 `config_version` 闸门）、`docs/ARCHITECTURE.md`
   （官方架构笔记）——判断"某段话是不是过期了"先查这三处。
4. 前端侧（若你要碰 UI）：`frontend/AGENTS.md` 是唯一官方入口，本书第 01/02 章对
   前端只做拓扑级描述，不深入。

### 4.4 判定资料过期的四把尺

任何外部资料（包括本书，虽然它钉死在 2672e209）拿回来先用四把尺量：

1. **路径尺**：出现 `backend/src`、`src.models.` → 过期（2.x 中期前）。
2. **配置尺**：提 `mcp_config.json`、顶层 `middlewares:`、Tavily 默认 → 过期。
3. **机制尺**：说"11 层中间件链" → 过期（现在是 35 链位，顺序由装配代码决定）。
4. **版本尺**：commit 早于本仓库基线、或 `config_version` 对不上当前 `config.example.yaml`
   → 以 CHANGELOG_zh.md + AGENTS.md + 源码为准，别照抄。
